Attention for the Vega II, designed from its requirements

With flash attention off, the M4 Max degrades with context; with it on, it does not. The Vega II is refused it by a vendor-family test. That control is the whole case — the gap is the software, not the silicon — This is the specification of that algorithm, written for a 64-wide machine with a large register file and no matrix units, phase by phase.

target YuE2-3B · q8_0 · decode machine Radeon Pro Vega II · Vega 20 · GCN 5.1 KV cache on Metal F32 · 512 B rows · 224 KiB/token measured now 80 ms/token @ 5,396

Corrections applied after verification

Three agents checked the machine, the workload and Apple's assumptions against the user's oracles and the engine source after this page was first published. Some of what they found reverses the original, so it comes first.

KV dtype
The cache is F32 on Metal, not F16. 512-byte rows, 224 KiB per token. The F16 path exists but is gated to CUDA/HIP/Vulkan. The kernel takes dtype as a parameter; F16 is free 2× headroom later.
R0, new
The explicit path's dominant cost is data movement this design had not identified. Per layer it REPEATs K and V from 8 heads to 16 and does four CONTs — six dispatches that only reshape, measured at 56% of step time. QK^T is not starved (104,512 independent dots at batch 2); only the AV reduction is. Consume the native [128, 8, S, B] layout, index GQA, never materialise: one dispatch per layer replaces nine.
R5a, new
The runtime over-scans. Cost tracks allocated cache steps (prefix + 5,120), not live context. A valid_steps bound with per-block early exit recovers ~24% of the context term.
range
Design for S = 4,000–12,000, common case 7,837 — not 24,576, which is the NAR ceiling the AR never reaches.
fixed floor
It is dispatch. After a perfect attention kernel 11.24 ms/token remains: 2.43 ms of weight traffic and 8.81 ms of 1,013 serialised dispatches at 8.7 µs each. Attention fusion removes 168 of them; the FFN chain is the rest.
withdrawn
"The Vega II beats the M4 Max on the same algorithm." The M4 Max's FA-off path is a different lowering (FlashGroupedViewKV, no CONT/REPEAT chain) and the Vega sweep ran CFG batch 2 where the song ran batch 1. Not the same graph. The conclusion stands on the FA-on/FA-off control alone.
Phase A
Cannot be chosen on paper. Lane-per-key needs L1 to hold 4 KiB per wave — 128 KiB at the occupancy R2 demands, against 16 KiB. And at head_dim 128 a 64-wide wave handles two KV rows per instruction in the lane-per-dim mapping, 1 KiB contiguous: wave64 is a structural fit there, not a cost. The register file is unobservable on this toolchain, so the mapping is measured — both are comptime variants of attention_bench.mojo.
measured
ILP knee 8 chains per lane (94% of peak). Occupancy ladder for 256-thread threadgroups: 1 TG/CU → 0.97×, 4 → 1.70×, 16 → 1.95× — the grid must reach ≥ 256 threadgroups, ideally ~1,024, so block size is a swept parameter. Bandwidth ceiling is instrument-dependent (647 triad vs 830 copy); this page quotes 647.
hazards
Threadgroup size from the probed width (a constant silently halves at 64 → NaNs, no error); barriers and cross-lane ops convergent; simd_ballot i64; llvm.vector.reduce expanded by hand.

The curve we are chasing

Everything in this document follows from one experiment. The M4 Max was run against itself with flash attention on and off while the context grew; the Vega II — which cannot run flash attention, because FLASH_ATTN_EXT is gated on simdgroup_matrix — was put on the same axes.

What was eliminated on the way here, each by measurement rather than reasoning: bandwidth (80 ms/token against a 3.9 ms traffic floor — 69× off), host-side dispatch (GGML_METAL_N_CB 1→8 changes nothing; CPU 11% busy), and concurrent dispatch (3%, and disabled anyway for producing wrong results). What remains is occupancy: sixteen threadgroups of serial work on a card that wants two and a half thousand waves in flight.

Requirements

Each traces to a measurement or to the machine. R-numbers are referenced throughout; the phase specifications below cite them.

R1
Parallelism must come from the context dimension. At batch 1 there are 16 heads of work (32 under CFG) for 64 CUs and ~2,560 wave slots. Heads and batch are exhausted; only the KV range is long. Split it into blocks; give each block its own workers; combine.
R2
Hide DRAM latency by wave switching, so keep each lane's live state small. GCN covers memory latency with ready waves, not cache. Occupancy is set by VGPRs per lane. Attention at decode is traffic-shaped — 619 MB of KV per token against ~7 MFLOP — so it wants occupancy, not the register blocking that served the GEMM.
R3
Read every K and V row coalesced, once. A row is head_dim 128 × f32 = 512 bytes as allocated today (f16 = 256 B by parameter). A wave64 instruction is 64 lanes. Whether a row is one clean access or 64 scattered ones is decided entirely by the lane→data mapping, which is therefore a requirement, not a detail.
R4
Exploit GQA 2:1. num_key_value_heads = 8 serve num_attention_heads = 16. Process both query heads of a KV head in the same threadgroup and K/V traffic halves: 619 → 310 MB per token at 8,000 context.
R5
Combine partials exactly with the online-softmax identity. Blocks yield (m, l, o[128]); merging is m = max(m₁,m₂); l = l₁e^(m₁−m) + l₂e^(m₂−m); o likewise. Intrinsic to attention. Since dispatch cost is measured to be negligible here, a second reduce kernel is acceptable.
R6
fp32 accumulation; exp must not dominate. ~3.6 M exponentials per token (8,000 × 16 heads × 28 layers). Even at quarter rate that is microseconds. Running max, sum and accumulators stay fp32.
R7
The oracle and the target already exist. The explicit-attention path produces correct audio and is the per-tensor reference. The M4 Max FA-on curve is the target shape. Success is "flat", not a number chosen in advance.

Layer 0 — decomposition

The grid is (KV head, context block). Not query head: the two query heads that share a KV head ride in the same threadgroup (R4). A block is 256 keys; a threadgroup is 4 waves of 64 lanes — the same 256-thread shape as kernel_mul_mm_w64, already validated on this card — and each wave owns 64 keys, one per lane.

grid
(8, ⌈ctx/256⌉, batch) threadgroups. Batch is 1, or 2 under CFG (positive and negative prompts).
threadgroup
256 threads, 4 waves. threadExecutionWidth = 64 is asserted by the probe on every pipeline already.
block
Swept, 64–512. Measured occupancy ladder for 256-thread threadgroups: 1 TG/CU → 0.97×, 4 → 1.70×, 16 → 1.95×, so the grid must reach ≥ 256 threadgroups at S ≈ 7,800 and ideally ~1,024. BLOCK 256 gives 256 TGs there; BLOCK 64 gives 1,000.
valid_steps
Per-block early exit at the live bound (R5a). Blocks entirely past it are never launched into work; the last block masks per lane.
serves
query heads 2h and 2h+1 of KV head h. Two independent accumulator sets per lane.

Phase A — scores · two candidate mappings, decided by the bench

The score for key j is a 128-long dot product with Q. Two mappings, both comptime variants of attention_bench.mojo. (a) lane ↔ key, drawn below: every lane forms its own dot product, Q is a broadcast, zero cross-lane ops — but 64 rows 4,096 B apart per instruction, resting on L1. (b) lane ↔ dim, two keys per wave: 32 lanes × float4 cover one 512 B row, so a 64-lane wave reads two keys per instruction, 1 KiB contiguous, then a 5-step shuffle reduction over 32 lanes per key pair, with ≤ 8 accumulator chains per lane (the measured ILP knee). (b) is the structurally coalesced one and wave64 halves its softmax and barrier count per key relative to Apple's 32-wide blocks. The register file cannot be read on this toolchain, so this is decided by throughput, as the fork's own nr0 sweep was.

input
K[block]: 64 rows × 128 × f16 per wave, from the KV cache at stride nb_k per key. Q₀,Q₁: staged once per threadgroup into LDS as fp32, RoPE already applied upstream.
lane state
s₀, s₁ fp32 accumulators; loop counter; one f16x2 load register. ~5 VGPRs live.
arithmetic
128 × 2 FMAs per lane. Loads: 128 halves per lane as 64 × 4-byte packed loads, converted to fp32 in-register.
cross-lane
None.
memory (a)
Per lane 512 B contiguous; rows 4,096 B apart across lanes. L1 pressure 4 KiB per wave, 128 KiB per CU at 8 TGs/CU against a 16 KiB L1. Expected to thrash; the bench decides.
memory (b)
1 KiB contiguous per wave instruction (two 512 B rows), fully coalesced; 4 FMAs then a 5-rung shuffle ladder per key pair, generated from the width.
tail
Lanes whose key index ≥ context set s = −∞ and skip loads. Because a wave is exactly 64 keys, the tail is a single lane predicate, not a loop bound.
serves
R1, R3, R4.

Phase B — softmax · two wave reductions per block

Each lane holds a raw score per head. Softmax needs the block maximum, then the exponentials, then their sum. On a 64-wide wave that is one simd_max and one simd_sum per head per block — six shuffle steps each — once per 64 keys, not once per key. That ratio is what makes Phase A's mapping pay: 256 FMAs of independent work per lane against 12 reduction steps.

cross-lane
simd_max then simd_sum, per head: 4 reductions per block per lane. At 64 lanes each is 6 shuffle steps — one more than at 32. The concrete, bounded cost of wave64.
numerics
fp32 throughout. exp(s − m) with m the block max keeps every argument ≤ 0; no overflow path exists. Masked keys carry s = −∞ → p = 0 and contribute nothing to l.
rescale
Wave-local running state across the wave's own blocks within a threadgroup is not needed — each wave handles exactly one 64-key block per threadgroup. Rescaling happens once, at the intra-threadgroup merge (Layer 4). This keeps Phase B stateless within a wave.
LDS
512 B per threadgroup for p; written at lane index, read broadcast. Bank-conflict free in both directions on 32-bank LDS with 4-byte entries.
serves
R5, R6.

Phase C — output · lane ↔ dim

The output for a block is o[d] = Σj pj V[j][d]. Keeping lane-per-key here would need a 64-lane reduction for every one of 128 output dimensions. So the mapping flips: lane d owns dims 2d, 2d+1 and loops over the 64 keys, reading pj as an LDS broadcast and V[j] as one coalesced 256-byte row across the wave. Two mappings in one kernel — each phase gets the one that makes its memory access clean and its arithmetic shuffle-free.

lane state
o₀[2], o₁[2] fp32; loop counter; one f16x2 load. ~6 VGPRs.
arithmetic
64 keys × 2 dims × 2 heads = 256 FMAs per lane. Same count as Phase A; the kernel is balanced across its two GEMVs.
cross-lane
None. p_j is a broadcast LDS read (all lanes same address → single bank, no conflict).
memory
Per row 256 B across 64 lanes at 4 B each: exactly the wave64 coalescing unit. 64 rows per block.
tail
Masked keys have p = 0 from Phase B; their V rows may still be loaded (harmless, in-bounds within the cache allocation) or skipped by a uniform branch on the block's valid count. Skip: it saves traffic on the last block only.
serves
R1, R3, R4.

Layer 4 — combining partials

After Phases A–C each wave holds, per head, a partial (m, l, o[128]) for its 64 keys. Two merges follow: four waves into one partial per threadgroup, through LDS; then all threadgroups of a head into the final output, in a second kernel. Both use the same identity (R5). The second kernel is trivially small, and dispatch cost is measured to be a non-issue here, so the main kernel stays simple.

intra-TG merge
Barrier; waves 1–3 write (m, l, o[128]) to LDS; wave 0 merges with the R5 identity into its own registers (lane d owns dims 2d, 2d+1 — the Phase C mapping, so no re-layout); wave 0 writes the threadgroup partial. 2,080 B of LDS.
scratch
partials[batch][16][nblocks][130] fp32, allocated by the host per graph at nblocks = ⌈ctx/256⌉. Same lifetime as any ggml intermediate.
reduce kernel
Grid (16, batch), one wave. Lane k folds partials k, k+64, … serially with the identity, then two wave reductions fold 64 lanes to one: m via simd_max, then rescaled l and o via simd_sum — o needs 128 sums, done as each lane owning two dims after a shuffle transpose through LDS. Normalise, write. Sub-millisecond in every case.
serves
R5, R7 (its output is bit-comparable to the explicit path).

Layer 5 — host integration

The kernel is selected, not substituted. ggml's FLASH_ATTN_EXT op already carries Q, K, V, an optional mask and a scale; the host's job is to route decode-shaped instances of that op to this kernel on a wave64 device and leave everything else exactly as it is.

capability
supports_op(FLASH_ATTN_EXT) currently returns has_simdgroup_mm. It becomes has_simdgroup_mm || (has_mm_w64 && decode_shaped(op)), where decode-shaped is n_queries ≤ 2, head_dim 128, K/V f16, and KV rows contiguous per head. Anything else on a wave64 device keeps returning false and falls back as today.
gate placement
This makes AUDIOCPP_DISABLE_FLASH_ATTN unnecessary for decode on AMD but still required for prefill, since the prefill kernels remain unported. The cleaner end state is for audio.cpp to consult supports_op per call rather than a process-wide switch; that is a small change in qwen_decoder.cpp and nar_runtime.cpp and is out of scope for the kernel itself.
dispatch
Two encodes per attention op: main kernel at grid (8, ⌈ctx/256⌉, batch) × 256 threads with LDS = 1 KB + 512 B + 2,080 B; reduce at (16, batch) × 64 threads. Scratch buffer from the graph allocator.
dials
GGML_METAL_FA_W64_DISABLE — the A/B dial, value-aware like MM_W64_DISABLE. Nothing else. The block size is structural and is not exposed.
apple silicon
Unreachable: has_mm_w64 is false there. The parity check (AIR at width 32, function-by-function) is rerun before commit as it was for the GEMM.

Two things change, and the measurement says the first is bigger: the six reshape dispatches per layer that were 56% of step time disappear (R0), and the remaining reads are done by ~1,000 waves instead of sixteen threadgroups (R1/R2). Then the over-scan stops (R5a). What the flat curve confirms or denies is whether, after all three, the card is bandwidth-shaped.

What is genuinely harder here

The register file is unobservable. Apple's driver lowers AIR→GCN as a black box; no VGPR count, no occupancy counter exists on this toolchain. The only instrument is end-to-end throughput plus the pipeline's reported max threads per threadgroup (1024 means light, 512/768 means register-heavy — this tree's own w64 GEMM reports 512). So every register figure on this page is a plan, and the bench brackets the blocking factor the way the fork's nr0 sweep did. That is also why Phase A ships as two variants rather than one.

Smaller costs, stated so they are not discovered later: a wave reduction is 6 shuffle steps rather than 5 — but once per 64 keys rather than 32, so 3.3× cheaper per key than Apple's; and a kernel with two lane mappings is two mental models to get right. What the hazard list adds: threadgroup size must come from the probed width, barriers must be unconditional, ballot must be the i64 form, and reductions are expanded by hand.

What is not harder: nothing here needs simdgroup_matrix, and nothing here needs a threadgroup size that is a multiple of 32 for its own sake. Those were consequences of Apple's design, not of attention.

Validation gates, in order

gate 1
Op-level. test-backend-ops -o FLASH_ATTN_EXT at the real shapes (head_dim 128, n_q 1–2, ctx 64…8,192), one op under the 30 s watchdog, against the CPU reference. NMSE below the op's tolerance — a number, not an impression.
gate 2
Per-tensor A/B on the card. New kernel against the explicit path on identical inputs, via GGML_METAL_FA_W64_DISABLE. Max abs and NMSE per layer. This catches what the synthetic shapes miss.
gate 3
The curve. ms/token at 200 / 800 / 1,600 / 3,200 / 6,400, two repeats. It must go flat — the dashed red line in the first figure. Phase A's variant is chosen here, and a flat curve that sits far above the intercept means the fixed floor — dispatch — is next.
gate 4
The oracle. Waveform check — peak, full-scale count, level count — then the full song, then the headphones. In that order, as always. No timing number is quoted before gate 4 passes.
